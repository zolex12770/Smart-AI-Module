**Phase 7 (async job system) — MVP done, real pg-boss on the existing Postgres, no Redis:**

- New package `packages/jobs`: a thin `JobQueue` wrapper around `pg-boss`, using pg-boss's **own, officially-maintained** `fromPglite` adapter (discovered while investigating how to connect pg-boss to an embedded PGlite instance — pg-boss ships first-class PGlite support, not just Redis/standard-Postgres) — confirms ADR-012's original pg-boss recommendation without needing any bridging code.
- Document ingestion (Phase 6) converted from a synchronous HTTP call to a real async job: `POST /api/v1/files` now returns `202` immediately with the document in `ingesting` status; a worker (registered in-process within `apps/api`) processes it moments later.
- **Real architectural constraint discovered and documented (ADR-027), not worked around with a fake separation:** a separate `apps/worker` OS process — as originally sketched in `docs/24_PROJECT_STRUCTURE.md` — cannot share the same PGlite database as `apps/api`, because PGlite is single-connection/embedded. Confirmed directly: running two processes against the same `DATABASE_DIR` crashed the WASM engine outright during this phase's own testing, not a graceful lock error. The worker therefore runs in-process within `apps/api` for now — a real, working job system with a documented, honest scaling boundary, not a shortcut. A genuinely separate worker process becomes possible once Phase 14 introduces a real standalone Postgres.
- **Verified three ways, catching two real, non-obvious findings along the way:**
  1. `packages/jobs/src/queue.test.ts` — a real in-memory PGlite instance, no mocks: basic enqueue/process; a genuine crash-recovery simulation (a worker handler that hangs forever, then a second `JobQueue` instance sharing the same PGlite handle — simulating a restarted worker — picks up the stale-locked job once pg-boss's own lock-expiry mechanism fires); and idempotency via `singletonKey`.
  2. **Real finding #1:** pg-boss's default `standard` queue policy does **not** deduplicate by `singletonKey` at all — only `exclusive`/`singleton`/`stately`/`short` policies do. The test initially failed against this wrong assumption; fixed by setting `policy: "exclusive"` on the queue, which is the actually-correct way to get the idempotency guarantee docs/07 describes.
  3. **Real finding #2:** passing `superviseIntervalSeconds`/`maintenanceIntervalSeconds` as explicit `undefined` (rather than omitting the keys) crashes pg-boss's constructor validation — caught immediately when actually booting `apps/api`, not by inspection; fixed by conditionally spreading only defined options.
  4. Full-process test through the running API: enqueued a real document-ingestion job, `taskkill`ed the API process immediately afterward (before the job could be claimed), then did a clean restart — the job still completed correctly, and the ingested document was confirmed genuinely searchable via RAG afterward.
- Cancellation is not yet wired into the job system's public surface — no current job type needs it (document ingestion is fast and its own status field already communicates progress).

- None blocking further work. Phase 2 (real LLM providers) needs at least one real API key from the user to verify end-to-end beyond adapter unit tests. Phase 14's actual provisioning needs a real GCP project/billing/authorization (ADR-011) — its Dockerfiles/Terraform/runbook are written but unverified beyond `terraform validate`/`plan` (see below).
- Remaining Phase 4 scope not yet done: git/web native tools (the `node`-only terminal allow-list is now argument-validated, per ADR-032, but still just `node`).
- The hydration-mismatch console warning noted after Phase 1 was not seen again during Phase 3/4 testing or Phase 10's real browser sessions — never reproduced; low priority, likely stale.
- **PGlite data-corruption risk (ADR-029, ADR-031):** a forceful process kill — or, as Phase 10 additionally found, `tsx watch`'s own internal restart with no external kill at all — can *sometimes* silently corrupt the local dev database, surfacing much later as a `RuntimeError: Aborted()` at boot. Confirmed timing-dependent, not guaranteed. A graceful-shutdown handler was added; Phase 9 confirmed directly (via a refused non-forceful `taskkill`) that this sandbox structurally cannot ever exercise it, for any process. If corruption recurs, the fix is to delete `apps/api/data/pgdata` and let it re-migrate fresh — it's disposable local dev data, never a real data-loss concern for an actual deployment.
- **ffmpeg render path unverified (ADR-030):** `processVideoRender`'s ffmpeg-present branch (the actual scale/pad/concat commands) has never run against a general-purpose ffmpeg — this sandbox has no such install (only Playwright's stripped screen-recording ffmpeg build, confirmed unable to decode GIF or encode mp4/h264). Every real run here correctly falls back to `renderStatus: "skipped_no_ffmpeg"`. Needs an environment with a full ffmpeg build on `PATH` to close out.
- **RBAC, SSRF protection (ADR-032):** explicitly deferred — no auth system and no URL-fetching tool exist yet respectively, so building either now would be decorative. Each has a stated unlock condition in docs/27.
- **No metrics, no OTLP-to-a-Collector export, no full agent-run trace coverage (ADR-033):** deferred — no Prometheus/Grafana (no Docker) to consume metrics, no Collector/GCP project to export traces to, and full `agent.run` tracing needs a start-now/end-later span lifecycle that doesn't exist yet (a real design task, not a missing line of code — see docs/27).
- **SSE-hijacked endpoints have no automated test coverage (ADR-034):** `chat.ts`'s `POST /api/v1/chat` and `agent.ts`'s `/events` use `reply.hijack()`, which doesn't observe cleanly through Fastify's `app.inject()`. Manually/Playwright-verified only — a stated gap, not silently missing.
- **CI has never actually run (ADR-035):** `.github/workflows/ci.yml` exists and every command was verified locally from a fresh build state, but this repo has no GitHub remote and the `gh` CLI isn't available in this sandbox — "CI green" is unproven until the repo is actually pushed somewhere and a real run is observed.
- **`docker build` has never actually run (ADR-037):** `apps/api/Dockerfile`/`apps/web/Dockerfile` exist and were reviewed line by line against the already-verified local build sequence, but no Docker install exists in this environment — neither image has ever actually been built.
- **`terraform apply` has never actually run (ADR-037):** `infrastructure/terraform/` was `init`ed and `validate`d for real (catching and fixing a genuine `dynamic` block/sensitive-value bug) and a real `terraform plan` reached a real "no GCP credentials" error rather than a config error, but no GCP project/credentials exist here — no resource has ever actually been created.
- **The coding agent's workspace is per-instance scratch (ADR-037, narrowed by ADR-040/041):** RAG's file input now arrives via a real upload into the asset store, so the only local-disk use left under `SANDBOX_ROOT` is the coding agent's working directory — fine for one run, not durable across instances; a product question tied to multi-file coding work, no longer a deploy blocker. The path-based `POST /api/v1/files` is dev-only on a deployment.
- **No malware scanning of uploads (ADR-041, docs/13 §12):** uploads pass an allow-list, declared-type check, and real content sniff, then go straight to ingestion; the provisioned `quarantine` bucket is unused. Acceptable for the current single operator, not for untrusted uploaders.
- **`CloudStorageAssetStore` has only been exercised against an emulator (ADR-040):** real GCS, Application Default Credentials, and the Terraform IAM bindings have never been in the loop together; the runbook's verify step names what to look for.
- **One accepted runtime moderate advisory (ADR-040):** `uuid@9 < 11.1.1` transitively under `gaxios` via `@google-cloud/storage` — vulnerable API not reachable as used (argued in docs/27), no non-breaking fix, CI gate unaffected. Re-check on every `@google-cloud/storage` upgrade.
- **The LLM pricing table is static, not live/DB-backed (ADR-038):** `packages/model-router/src/cost-estimator.ts` needs a manual update whenever a priced provider changes its rate — this already happened twice during the research that populated it. No automated staleness detection exists.
- **Cost estimation is LLM-only (ADR-038):** image/video usage is quota-enforced (real unit/second counts) but not cost-estimated in dollars, since no real image/video provider is chosen yet to price against (ADR-009) — `estimatedCostUsd` is correctly `null`, never fabricated, for those rows.
