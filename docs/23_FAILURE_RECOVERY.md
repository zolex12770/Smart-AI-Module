# Failure Recovery

A catalog of failure modes and the concrete recovery mechanism for each — every row must map to something implemented, tested per [[21_TESTING_STRATEGY]]'s fault-injection approach on mock providers, not just described in prose.

| Failure mode | Detection | Recovery |
|---|---|---|
| LLM provider timeout / 5xx | Request-level timeout in the provider adapter ([[04_MODEL_PROVIDER_RESEARCH]]) | Bounded retry with exponential backoff (per NFR-009's hard cap on retry count) → on exhaustion, [[12_MODEL_ROUTING]]'s fallback to a compatible alternate provider, re-checked against [[22_COST_AND_QUOTA_STRATEGY]] before the fallback call → on total exhaustion, task transitions to `FAILED` with a user-facing error, never a silent hang |
| LLM provider rate limit (429) | Status code + provider-specific rate-limit headers where available ([[28_API_PROVIDER_MATRIX]] notes Google lacks these — reactive backoff only) | Backoff honoring `Retry-After` when present; queued redelivery via the job system for non-interactive calls, immediate user-facing "rate limited, retrying" state for interactive chat |
| Agent task crash mid-execution (process restart) | Task/step status left in a non-terminal state (`EXECUTING`, `WAITING_FOR_TOOL`) with no corresponding completion event on restart | Per [[11_AGENT_LOOP]]'s crash-safe design: resume from the last **committed** step, never blindly re-run a step whose side effect may have already happened — a mutating tool call found in an ambiguous state (started, no confirmed result) is never auto-retried; it is reconciled via an idempotency check or escalated to human approval (this is the single most important rule from the agent-loop research, directly preventing double-sends) |
| Job worker crash mid-job | pg-boss's own visibility-timeout/lease mechanism ([[07_LONG_RUNNING_JOB_ARCHITECTURE]]) | Job becomes re-claimable by another worker after lease expiry; handlers are written idempotently keyed on the job's `idempotency_key` so a re-claimed job doesn't duplicate its billable side effect (NFR-004) |
| One scene fails in a long-form video job | Scene-level job status in `scene_manifests` ([[14_DATABASE_ARCHITECTURE]]) | Only the failed scene re-enqueues; completed scenes and the assembled-so-far timeline are untouched — the concrete resumability requirement from FR-043, verified by a test that deliberately fails one scene |
| MCP server disconnects / returns malformed data | Transport-level error or schema validation failure on the tool response ([[10_TOOL_AND_MCP_ARCHITECTURE]]) | Tool call fails cleanly, surfaced to the agent as a tool error (not a crash); repeated failures from the same MCP server can auto-disable it pending user review, per that server's trust tier |
| Database temporarily unavailable | Connection error from the repository layer | API returns 503 with `Retry-After`; in-flight jobs are not lost (pg-boss/Postgres persistence means "unavailable" is transient, not data-destroying) — no in-memory-only state exists for anything durable, by construction of [[14_DATABASE_ARCHITECTURE]] |
| Coding agent's multi-file edit partially applied before a failure | Change log recorded per file as it's applied (FR-013's audit trail) | Every applied-so-far file is known and reversible (git-based rollback of just those files, since the coding agent operates on a real repo with version control) — never a whole-repo rewrite to begin with (FR-011), which bounds the blast radius of a partial failure |
| Untrusted content attempts to trigger a high-risk action | Trust-level tagging on content source ([[13_SECURITY_ARCHITECTURE]]) | The action is gated behind mandatory human approval regardless of how the model responded to the injected content — this is an architectural gate, not a detection-and-block heuristic, per that doc's core recommendation |
| Runaway agent loop (would call a paid model unboundedly) | Step/retry counters enforced in `agent-core`, independent of model behavior | Hard step-count ceiling per task (NFR-009); exceeding it forces `FAILED`, never an infinite loop — tested explicitly, not just assumed |

## Circuit breaking

A provider with a sustained elevated error rate (tracked via the metrics in [[20_OBSERVABILITY]]) is temporarily marked unavailable in the `ModelRegistry`/`CapabilityRegistry` so the router stops sending it traffic for a cooldown window, rather than every concurrent request individually discovering the same outage via its own timeout — this is what keeps a provider outage from becoming a thundering-herd retry storm against that provider.

## What "graceful failure" means here, concretely

Per NFR-003: every failure mode above ends in one of exactly three states — a successful fallback/retry the user never sees, a clear user-facing error with no leaked internal detail (per [[15_API_ARCHITECTURE]]'s error shape), or a resumable paused/failed state the user can act on (retry, approve, or accept). An unhandled exception reaching the client is treated as a bug in this design, not an acceptable outcome — enforced by the central error-handling middleware in [[17_BACKEND_ARCHITECTURE]].
