# Risks & Limitations

Honest accounting, kept current. See [[FINAL_AUDIT|FINAL_AUDIT]] (now exists, produced at Phase 15, 2026-09-02) for the point-in-time audit and what it found/fixed; this file tracks standing, structural risks going forward.

## Structural limitations (true regardless of how well we build)

- **No provider can generate a single 20+ minute video clip as of this research (2026).** Confirmed concretely: real per-call duration ceilings across every provider surveyed sit between 5 and 25 seconds (Veo 3.1: 8s; Sora 2: up to 12s, Sora 2 Pro: up to 25s; Runway Gen-4: up to 10s; Luma Ray2: up to 9s; Kling: 5s default/10s max) — see [[06_VIDEO_GENERATION_RESEARCH]]. "Extend" features chain multiple short calls; they do not raise the real per-call ceiling. Long-form video is necessarily a scene-decomposition-and-assembly pipeline ([[07_LONG_RUNNING_JOB_ARCHITECTURE]]), not a native capability of any vendor API. We will not claim otherwise in product copy.
- **Live illustration of why this platform is provider-agnostic:** research (2026-08-31) found OpenAI's entire Sora 2 API is scheduled to shut down September 24, 2026 — roughly three weeks out. A platform hardcoded to one video vendor would face an imminent forced rewrite; the `VideoProvider` abstraction ([[06_VIDEO_GENERATION_RESEARCH]]) exists precisely so a vendor deprecation is a config/adapter change, not an architecture change. This is also one more reason ADR-009 (mock-first, real integration only once credentials exist) is the right sequencing — we are not currently exposed to this deprecation at all.
- **Cross-scene visual/character consistency in generated video is best-effort, not guaranteed**, even with reference images/seeds/character sheets. This is a known limitation of current generative video models, not a bug in our orchestration.
- **RAG retrieval quality is bounded by chunking/embedding choices and can miss or misattribute information**, especially on documents with complex layout (tables, scanned images). Citations reduce but do not eliminate the risk of a wrong answer being presented as document-grounded. As of Phase 6, this is more pronounced than the general case: the embedding is a real deterministic feature-hashed vector (lexical/keyword overlap), not a learned semantic one ([[26_DECISIONS]] ADR-026) — a question phrased with different words than the source document may retrieve nothing relevant even though the answer exists in the corpus. Plain text/Markdown, real PDF, and real DOCX ingest today (docs/26_DECISIONS.md ADR-036); CSV is not yet parsed, and PDF/DOCX extraction is plain paragraph text only — no layout/table/heading-structure awareness, and no OCR for scanned PDFs.
- **Prompt injection cannot be fully eliminated**, only mitigated (trust-level separation, approval gates on high-risk actions per [[13_SECURITY_ARCHITECTURE]]). Any agent that reads untrusted content and can take actions has residual risk.
- **Mock providers validate interface/orchestration correctness, not real output quality.** Passing all tests against `llm-mock`/`image-mock`/`video-mock` does not prove the real provider integration behaves identically — real-provider validation is a separate, explicit step once credentials exist (ADR-009).

## Project/environment-specific risks (current as of 2026-09-02)

| Risk | Impact | Mitigation | Status |
|---|---|---|---|
| No LLM provider API keys configured | Cannot validate real-provider adapters end-to-end until user supplies at least one key | MVP runs fully on mock provider (ADR-006, ADR-010); real adapters built and unit-tested against recorded fixtures, integration-tested once a key is available | OPEN — tracked in PROJECT_STATUS.md |
| No Docker/gcloud/terraform CLI on dev machine | Cannot locally exercise Postgres/Redis via Compose; `docker build` (Phase 14's own stated exit criterion, [[26_DECISIONS]] ADR-037) has never actually run against `apps/api/Dockerfile`/`apps/web/Dockerfile` — reviewed line by line instead | Phase 1–5 avoided the dependency entirely (SQLite, in-process jobs); a real `terraform` binary was downloaded and used for genuine `init`/`validate`/`plan` against `infrastructure/terraform/` (catching a real bug), which Docker's absence didn't allow for the Dockerfiles; cloud deployment stays documentation/IaC-only until explicitly authorized (ADR-011) | OPEN — needs a real Docker install to close |
| Solo engineering effort (one user, one agent) building a very large surface area | High risk of scope creep or shipping breadth without depth | Roadmap ([[25_IMPLEMENTATION_ROADMAP]]) enforces phase gating — each phase must be verified working before the next starts; feature matrix tracks honest status, not aspirational status | Ongoing discipline, not a one-time fix |
| Video/image generation costs can be large and unpredictable once real providers are wired in | Runaway spend if quotas aren't enforced before real keys are added | FR-063 quota enforcement now real and live-verified for LLM tokens, daily image count, and monthly video-seconds ([[26_DECISIONS]] ADR-038) — must remain wired in when real media provider integration (FR-041/FR-042 real mode) lands, not re-added after. Real dollar cost estimation is LLM-only today (image/video have no real provider chosen yet to price against, ADR-009) — extend `packages/model-router`'s cost table the same day a real image/video provider key exists | Gate substantially closed for LLM; extend to real image/video pricing alongside that integration, not after |
| The LLM pricing table (`packages/model-router/src/cost-estimator.ts`, ADR-038) is a static, version-controlled file, not live-fetched or DB-backed | Will silently under/over-report cost the moment a priced provider changes its rate — this already happened twice during the research for this exact table (both entries had changed since docs/04 was written) | A deliberate MVP trade-off (docs/22's `models.cost_profile` DB design is real, larger work not yet justified) — revisit if real spend ever depends on this number being precise rather than directionally useful | OPEN — no automated staleness detection exists; a manual re-check is the only mitigation today |
| Single relational database (Postgres+pgvector) may not scale to very large embedding volumes | Degraded RAG latency at high document/user counts | Documented migration path to a dedicated vector DB in [[09_RAG_ARCHITECTURE]]; not a current blocker | Accepted for current scale |
| No OS-level sandboxing around spawned MCP server subprocesses ([[26_DECISIONS]] ADR-021) | A compromised/malicious local MCP server would have full OS-user privileges, per [[10_TOOL_AND_MCP_ARCHITECTURE]] §2.5 | Only connect to servers whose trust is otherwise established (the reference filesystem server, scoped to our own sandbox dir); containerize/restrict-user spawns before connecting to any less-trusted server | OPEN — required before onboarding untrusted MCP servers |
| Agent-core's planner is deterministic/rule-based, not LLM-driven ([[26_DECISIONS]] ADR-018) | Can only handle four known task shapes; cannot reason about arbitrary user requests yet | By design until Phase 2 supplies a real LLM key worth planning with; the state machine/persistence/tool layers underneath don't need to change when it's swapped | Planned, not a defect |
| Local Postgres is PGlite (embedded WASM, single-process) ([[26_DECISIONS]] ADR-025) | Not suitable for a multi-instance production deployment as-is; confirmed directly — two processes opening the same PGlite `dataDir` concurrently crashes the WASM engine (not a graceful lock error) | Schema/queries are genuinely Postgres-compatible; `createPostgresDb()` (ADR-037) now provides a real, if unprovisioned, standalone-Postgres connection path that swaps the connection, not the schema — verified with a real connection-attempt test, not yet with a real running server (no Docker to run one locally). Never run two `npm run dev` instances against the same `DATABASE_DIR`. | Accepted for current (local/single-instance) scope; the code-level blocker for a real deployment is closed, the infrastructure is not provisioned |
| Job worker runs in-process within `apps/api`, not a separate `apps/worker`/Cloud Run Worker Pool ([[26_DECISIONS]] ADR-027, ADR-037) | A slow/expensive job could compete with HTTP request handling in the same process — not yet an issue since job types so far (document ingestion, mock image generation) are fast | Revisit once a genuinely expensive job type exists (e.g. real media generation). Real standalone Postgres connectivity now exists (ADR-037) so the technical reason the worker couldn't be separate is gone, but actually splitting it needs a small, currently-unbuilt code change (an env-gated worker-only boot mode) — `infrastructure/terraform/` deliberately deploys the current, tested, combined topology rather than assuming that split already happened | Accepted; the PGlite constraint that originally forced this is resolved, the separation itself is still a stated follow-up |
| Local-disk asset storage and the RAG/coding-agent sandbox root do not survive Cloud Run's execution model ([[26_DECISIONS]] ADR-037) | `packages/media`'s `LocalAssetStore` and `SANDBOX_ROOT` both write to the container's local filesystem, which is ephemeral and not shared across instances or scale-to-zero cycles — image/video generation output and RAG-ingested files would not reliably persist on a real Cloud Run deployment | Cloud Storage buckets are already provisioned by `infrastructure/terraform/` ahead of the code that would use them; a real `CloudStorageAssetStore` (and a rethink of what `SANDBOX_ROOT` means for a stateless container) is real, scoped, currently-unbuilt follow-up work, not silently assumed solved by the buckets existing | OPEN — a real prerequisite for an actually-working cloud deployment, found while writing the deployment runbook |
| `infrastructure/terraform/` has never actually been applied ([[26_DECISIONS]] ADR-037) | No GCP project/credentials exist in this environment | `terraform validate` passed for real (after finding and fixing a genuine `dynamic` block/sensitive-value bug via isolated bisection) and `terraform plan` against a placeholder project reached a real "no GCP credentials" error rather than a config error — structurally sound as far as this sandbox can confirm, but no resource has ever actually been created | OPEN — blocked on a real GCP project + explicit authorization (ADR-011), not on missing/unverified code |
| A forceful process kill — or even `tsx watch`'s own internal restart — can silently corrupt PGlite's on-disk data, surfacing much later ([[26_DECISIONS]] ADR-029, ADR-031) | Observed directly, three times now across two different triggers: (1)/(2) a `taskkill /F`-terminated process left the dev database readable for simple queries but crashed hard (`RuntimeError: Aborted()`) on the next schema migration, confirmed timing-dependent (a later forceful kill of the same server did *not* corrupt it); (3) in Phase 10, `tsx watch` restarting the API on its own (no external kill at all, just a normal file-save-triggered restart) produced the identical crash on the very next boot — a materially different, more concerning trigger since it implies the old process may not always release its PGlite file handle before the new one opens it | Graceful shutdown handler added (`SIGINT`/`SIGTERM` closes PGlite cleanly) — but a direct `taskkill /PID` (no `/F`) against the running dev server was attempted in Phase 9 and Windows refused outright ("This process can only be terminated forcefully"), confirming no tool in this sandbox can ever deliver a graceful signal to this process; the Phase 10 `tsx watch` incident additionally suggests the risk isn't fully contained to *external* forceful kills. If a `RuntimeError: Aborted()` ever recurs at boot, the fix is to wipe and re-migrate the (disposable, local-only) data directory, not to debug application code. | OPEN — needs both real graceful termination (Linux/Docker/Cloud Run) and a closer look at `tsx watch`'s own restart sequence |
| The ffmpeg-present branch of the video-render stage (`processVideoRender`, [[26_DECISIONS]] ADR-030) has never been exercised | This sandbox has no general-purpose ffmpeg installed — Playwright's own bundled ffmpeg build was located and confirmed to run, but it's a stripped screen-recording build (no GIF demuxer, no libx264/mp4 muxer) so it can't stand in for a real one. The scale/pad/fps-normalize-then-concat commands follow docs/07 §2.2 stage 8's documented approach and use the same safe-spawn pattern as `packages/tools/src/native/terminal.ts`, but that is not a substitute for having actually run them — an untested command-line flag or path-escaping edge case would not have surfaced yet | Verify on a machine/container with a full ffmpeg build on `PATH` before relying on real video assembly; until then, every real run here honestly reports `renderStatus: "skipped_no_ffmpeg"` rather than a fabricated file | OPEN — needs an environment with ffmpeg to close |
| No RBAC/tenant isolation ([[13_SECURITY_ARCHITECTURE]] §2, [[26_DECISIONS]] ADR-032) | Every operation runs as a single implicit operator (`SINGLE_OPERATOR_OWNER_ID`) — there is no per-user authorization boundary at all | Building RBAC without a real auth system would be decorative; unlocks once a real OIDC/OAuth2 provider is integrated (a substantial phase of its own) | OPEN — accepted for the current single-operator scope, not started |
| No SSRF protection ([[13_SECURITY_ARCHITECTURE]] §10, ADR-032) | N/A today — no tool fetches an arbitrary URL (the web/browsing tool is deferred, tracked since Phase 4) | Build SSRF defenses (egress allow-list, post-DNS-resolution IP validation) at the same time the web-fetch tool is built, not before | OPEN — blocked on a feature that doesn't exist yet, not urgent |
| A CI workflow exists (`.github/workflows/ci.yml`, incl. `gitleaks` secret-scanning) but has never actually run ([[13_SECURITY_ARCHITECTURE]] §3, ADR-035) | Every command in the workflow was verified locally from a genuinely fresh build state (catching and fixing a real step-ordering bug), but "CI green" per docs/25 Phase 13's exit criterion is unproven the one way that would fully confirm it | This repo has no GitHub remote in this environment and the `gh` CLI isn't installed here — pushing the repo somewhere and watching the first real run is the only way to close this, the same class of gate ADR-011 applies to real cloud provisioning | OPEN — blocked on the repo being hosted somewhere, not on missing code |
| No metrics, no OTLP-to-a-Collector export, no full agent-domain trace coverage ([[20_OBSERVABILITY]], ADR-033) | Can't yet answer "how is the platform trending" from a dashboard, only reconstruct one request/job at a time from logs/console spans; an agent run's human-approval-pausable lifecycle isn't represented as a single trace (only its two most expensive sub-operations, `gen_ai.chat` and `job.process`, are) | Structured logs + console-exported traces already give per-request/per-job reconstruction today (verified live for one chat and one job — the current phase's actual exit criterion); metrics need Prometheus/Grafana (no Docker), full agent-run tracing needs a start-now/end-later span lifecycle tied to task persistence (a real design task, not a missing line of code) | OPEN — revisit metrics once Docker exists; revisit agent-run spans as a dedicated follow-up |

## Explicitly out of scope for the initial working system (see [[01_REQUIREMENTS]] non-goals)

- Foundation model training/fine-tuning.
- Public multi-tenant self-serve billing.
- Any real image/video/cloud spend without explicit, separate user authorization at that specific step.
