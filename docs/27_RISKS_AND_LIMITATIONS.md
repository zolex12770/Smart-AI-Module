# Risks & Limitations

Honest accounting, kept current. See [[FINAL_AUDIT|FINAL_AUDIT]] (created at the end of the program) for the point-in-time audit; this file tracks standing, structural risks.

## Structural limitations (true regardless of how well we build)

- **No provider can generate a single 20+ minute video clip as of this research (2026).** Confirmed concretely: real per-call duration ceilings across every provider surveyed sit between 5 and 25 seconds (Veo 3.1: 8s; Sora 2: up to 12s, Sora 2 Pro: up to 25s; Runway Gen-4: up to 10s; Luma Ray2: up to 9s; Kling: 5s default/10s max) — see [[06_VIDEO_GENERATION_RESEARCH]]. "Extend" features chain multiple short calls; they do not raise the real per-call ceiling. Long-form video is necessarily a scene-decomposition-and-assembly pipeline ([[07_LONG_RUNNING_JOB_ARCHITECTURE]]), not a native capability of any vendor API. We will not claim otherwise in product copy.
- **Live illustration of why this platform is provider-agnostic:** research (2026-08-31) found OpenAI's entire Sora 2 API is scheduled to shut down September 24, 2026 — roughly three weeks out. A platform hardcoded to one video vendor would face an imminent forced rewrite; the `VideoProvider` abstraction ([[06_VIDEO_GENERATION_RESEARCH]]) exists precisely so a vendor deprecation is a config/adapter change, not an architecture change. This is also one more reason ADR-009 (mock-first, real integration only once credentials exist) is the right sequencing — we are not currently exposed to this deprecation at all.
- **Cross-scene visual/character consistency in generated video is best-effort, not guaranteed**, even with reference images/seeds/character sheets. This is a known limitation of current generative video models, not a bug in our orchestration.
- **RAG retrieval quality is bounded by chunking/embedding choices and can miss or misattribute information**, especially on documents with complex layout (tables, scanned images). Citations reduce but do not eliminate the risk of a wrong answer being presented as document-grounded. As of Phase 6, this is more pronounced than the general case: the embedding is a real deterministic feature-hashed vector (lexical/keyword overlap), not a learned semantic one ([[26_DECISIONS]] ADR-026) — a question phrased with different words than the source document may retrieve nothing relevant even though the answer exists in the corpus. Only plain text/Markdown ingest today; PDF/DOCX/CSV are not yet parsed.
- **Prompt injection cannot be fully eliminated**, only mitigated (trust-level separation, approval gates on high-risk actions per [[13_SECURITY_ARCHITECTURE]]). Any agent that reads untrusted content and can take actions has residual risk.
- **Mock providers validate interface/orchestration correctness, not real output quality.** Passing all tests against `llm-mock`/`image-mock`/`video-mock` does not prove the real provider integration behaves identically — real-provider validation is a separate, explicit step once credentials exist (ADR-009).

## Project/environment-specific risks (current as of 2026-08-31)

| Risk | Impact | Mitigation | Status |
|---|---|---|---|
| No LLM provider API keys configured | Cannot validate real-provider adapters end-to-end until user supplies at least one key | MVP runs fully on mock provider (ADR-006, ADR-010); real adapters built and unit-tested against recorded fixtures, integration-tested once a key is available | OPEN — tracked in PROJECT_STATUS.md |
| No Docker/gcloud CLI on dev machine | Cannot locally exercise Postgres/Redis via Compose, cannot provision or test real cloud deployment | Phase 1–5 avoid the dependency entirely (SQLite, in-process jobs); Docker Desktop documented as a prerequisite before Phase 6; cloud deployment stays documentation/IaC-only until explicitly authorized (ADR-011) | OPEN, non-blocking for current phase |
| Solo engineering effort (one user, one agent) building a very large surface area | High risk of scope creep or shipping breadth without depth | Roadmap ([[25_IMPLEMENTATION_ROADMAP]]) enforces phase gating — each phase must be verified working before the next starts; feature matrix tracks honest status, not aspirational status | Ongoing discipline, not a one-time fix |
| Video/image generation costs can be large and unpredictable once real providers are wired in | Runaway spend if quotas aren't enforced before real keys are added | [[22_COST_AND_QUOTA_STRATEGY]] and FR-063 must ship before real media provider integration (FR-041/FR-042 real mode) goes live, not after | Planned gate — do not skip |
| Single relational database (Postgres+pgvector) may not scale to very large embedding volumes | Degraded RAG latency at high document/user counts | Documented migration path to a dedicated vector DB in [[09_RAG_ARCHITECTURE]]; not a current blocker | Accepted for current scale |
| No OS-level sandboxing around spawned MCP server subprocesses ([[26_DECISIONS]] ADR-021) | A compromised/malicious local MCP server would have full OS-user privileges, per [[10_TOOL_AND_MCP_ARCHITECTURE]] §2.5 | Only connect to servers whose trust is otherwise established (the reference filesystem server, scoped to our own sandbox dir); containerize/restrict-user spawns before connecting to any less-trusted server | OPEN — required before onboarding untrusted MCP servers |
| Agent-core's planner is deterministic/rule-based, not LLM-driven ([[26_DECISIONS]] ADR-018) | Can only handle four known task shapes; cannot reason about arbitrary user requests yet | By design until Phase 2 supplies a real LLM key worth planning with; the state machine/persistence/tool layers underneath don't need to change when it's swapped | Planned, not a defect |
| Local Postgres is PGlite (embedded WASM, single-process) ([[26_DECISIONS]] ADR-025) | Not suitable for a multi-instance production deployment as-is; confirmed directly — two processes opening the same PGlite `dataDir` concurrently crashes the WASM engine (not a graceful lock error) | Schema/queries are genuinely Postgres-compatible; Phase 14's Cloud SQL plan swaps the connection, not the schema, when real multi-instance scale is needed. Never run two `npm run dev` instances against the same `DATABASE_DIR`. | Accepted for current (local/single-instance) scope |
| Job worker runs in-process within `apps/api`, not a separate `apps/worker` ([[26_DECISIONS]] ADR-027) | A slow/expensive job could compete with HTTP request handling in the same process — not yet an issue since the only job type (document ingestion) is fast | Revisit once a genuinely expensive job type exists (e.g. real media generation) or Phase 14's real standalone Postgres removes the single-connection constraint | Accepted, direct consequence of the PGlite constraint above |

## Explicitly out of scope for the initial working system (see [[01_REQUIREMENTS]] non-goals)

- Foundation model training/fine-tuning.
- Public multi-tenant self-serve billing.
- Any real image/video/cloud spend without explicit, separate user authorization at that specific step.
